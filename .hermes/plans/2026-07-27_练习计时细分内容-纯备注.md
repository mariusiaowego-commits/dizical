# Plan: 练习计时细分内容 (practice-session-detail)

> **For Hermes:** 本计划覆盖 PRD `AI-PRD-练习计时细分内容-260727.md` 的实现路径。先开 feature worktree，每阶段小 commit → 测试 → push → PR；不在父指令前 commit。
> **范围:** 仅 PRD 范围（每次科目计时细分内容），不碰"一天 N 场"/"AI 摘要"/"加速模式"/"语音录入"。

**Goal:** 让每次计时保存独立的 session（含速度+细节），不破坏现有 `daily_practices` 汇总、成就、报表、小程序。

**Architecture:** 新增 `practice_sessions` 事实表 + 写时事务化同步 `daily_practices.items` 汇总 + append audit。读时双轨（items 旧路径 + sessions 新路径），旧客户端零回归。前端在 `practice.html` 计时面板内增加"本次练习"区（音符/BPM/内容），今日记录改"科目汇总头 + session 列表"。

**Tech Stack:** 沿用项目现状 FastAPI + SQLite + 原生 HTML/JS + 内联 SVG，不引新依赖。参考 Kimai 的 timesheet entry 思路（一次计时 = 一条事实），但不复制其代码/数据模型。

### 任务 1.2：Database 层 CRUD

**Modify:** `src/database.py`

新增方法（接 PRD §5 字段 + 走 `db._get_connection()`，**不要自己 `sqlite3.connect`**）：

- `create_practice_session(...) -> Dict` — 校验 tempo_note 白名单 ♪/♩、BPM 40–150、minutes > 0、content 长度 ≤ 200
- `get_practice_sessions(date, item_id=None) -> List[Dict]`
- `delete_practice_session(session_id) -> None` — 走 BEGIN IMMEDIATE，删 session → 重算 daily 汇总 → 写 audit
- `save_practice_session_and_daily_summary(date, item, item_id, minutes, tempo_note, tempo_bpm, content, content_source, practice_at=None, is_extra=False) -> Dict` — **核心事务方法**：
  1. 校验
  2. `BEGIN IMMEDIATE`
  3. 读 daily 记录（无则视为空）
  4. 写 session
  5. `save_daily_practice` 的 items 累加逻辑（**不直接调 save_daily_practice**——它会再发一次 audit，污染；重写一份只更新 items JSON + total_minutes）
  6. `append_behavior_log` 写一条 `{enter_time, item, item_id, minutes, session_id, content, tempo_note, tempo_bpm}` 审计 entry
  7. `COMMIT`
  8. 异常 rollback + raise

**实现细节：**
- 跨后端 SQLite 兼容：跟既有 `save_daily_practice` 一样走 `conn.execute(...)`，不引 `db_adapter.py`（dizical 主仓目前不需要 MySQL adapter，那是 `feat/p4-phase1b-staging` 的事；本次不动 database_mysql.py）
- 重复跑迁移的 safety 已在阶段 1.1 处理；CRUD 层不重复防御

## 风险与明确取舍

1. **旧 `daily_practices.items` JSON 不能丢。** 旧成就（`src/achievement_definitions.py` calc_all）、旧报表（`src/practice_query.py`）、小程序读 `items`。新表是**叠加**，不是替换。
2. **不写"猜内容"的迁移。** 旧数据 content = '' + content_source='legacy'，UI 显式标"未填写练习内容"。绝不把老师要求文本或日记文本当 session 细节。
3. **不引新依赖。** FastAPI / SQLite / 原生 JS / 内联 SVG 全部够用。Pydantic 已有但本端不引（项目既有路由风格不强制）。
4. **事务必须原子。** session 写 + daily 改 + audit append 任一失败全部回滚。**这是 v2 撤销功能的根基**，不能省。
5. **不把 session 真相塞进 `behavior_log` JSON。** audit 表是审计用途，content 字段在 audit 里冗余存储，破坏审计语义。
6. **dizical-minip 暂不动（7-27 dad 拍板等 minip 并行改动合 main 后再评估）。** 评估后写入 changelog 标 🟡，dad 单独决定。
7. **本地 SQLite 红线：** 迁移前必备份，迁移不删原数据。
8. **本计划不含语音转文字**（dad 7-27 明确取消），不写 MediaRecorder / TranscriptionProvider / Hermes STT 任何引用。
9. **速度默认值查"最近一次 session"会引入额外 GET。** 阶段 1.4 必须用临时 session 表（不建新表），并且缓存 5s（避免每次切科目打 2 次后端）。或者**优化方案**：把最近 session 的 tempo 字段冗余存到 `practice_items` 表的 `last_tempo_note/last_tempo_bpm` 列，每次 session 写入时同步更新（**1 次写放大 1 次查 = 不需要专门查 session**）。这个权衡在 plan 阶段 1.2 决定，**推荐用冗余列方案**（性能 + 简单）。
10. **前端 disabled 必填门槛**（Q3=A 拍板）会改变现有 UX：以前随便点也能打卡的逻辑不再成立。**做完后必须**：
    - 真实录 1 次：选科目 → 内容空 → 按钮 disabled（截图记录）
    - 填内容 → 按钮 enabled → 提交 → 验证 session 落库
    - 跨日 / 跨科目 / 切回去重选 5 次 → 速度默认值符合 Q1=B 优先级
