## 二、❌ 必须纠正的 3 处

### 分歧 1（严重）：agy 的「两模式判定」会判错，我已实测证伪

agy 的方案 §3.1 写：
> 「卡片根容器统一 `container-type: inline-size`。当 `inline-size >= 350px` 时自动激活 Expand 模式。」

**实测证伪**（440 组合3，轨道 `flex-direction: column` 即真实 feed 模式）：

```
440 实际轨道方向 = column        ← 这是纵向 feed 流
各卡宽度 = A:408  B:408  D:408  R:408

按 agy 规则（>=350 判 expand）：
  A w=408 → EXPAND ⚠ 但实际是 feed 纵向流
  B w=408 → EXPAND ⚠
  D w=408 → EXPAND ⚠
  R w=408 → EXPAND ⚠
```

**4 张卡全部判错。** 根因：feed 模式下卡片宽度 = 容器全宽（408px），本来就 >350px。
**宽度不能区分两种模式 —— 因为两种模式下卡片都可能是宽的。**
真正能区分的是**轨道方向**（row = 横向扩展 / column = 纵向 feed），这个信息只有画布知道。

→ **采纳 Codex 方案 §2.1：由画布显式下发 `html.cz-expand` / `html.cz-feed`，卡片只响应这两个 class，不做自身宽度推断。**
（agy 的 container query 可以保留，但只能用来做**卡内自适应**（如 D 卡在 expand 下要不要双栏），不能用来**判定模式**。）

### 分歧 2（严重）：agy 把「单一真源」排在最后，这是顺序错误

| | Codex 方案 | agy 方案 |
|---|---|---|
| 单一真源（抽 cards/ + 构建注入） | **S1（第 2 步）** | **阶段 5（最后一步）** |

agy 的阶段 1-4 全部在 880KB 的 `canvas-01.html` 里做视觉改造，**最后才抽文件**。
后果：4 轮大改都在同一个巨型文件里进行，每一轮都可能像过去几轮一样「改 A 卡误伤 B 卡」，而且抽文件时还要把这些改动再搬一次（搬运过程本身就会引入新漂移）。
**这正是用户说的「改来改去没改对」的机制，不能重演。**

→ **采纳 Codex 顺序：先 S0 建 verify.py、再 S1 抽源、再 S2 模式改造，然后才动视觉。**
agy 的阶段 1-4 内容照用，只是把执行顺序挪到地基之后。

### 分歧 3（中）：agy 的「解除 overflow:hidden」会削弱露出比遮罩，需加约束

agy §5.1 主张把 `.cz-astack-crown`、`.dash-integrated-slot` 的 `overflow:hidden` 统一改 `visible`。

**实测风险**（强制 inline `overflow:visible` 后测）：

```
BEFORE  paintedPx=26  cardPanel=0  slotPanel=0
AFTER   paintedPx=27  cardPanel=0  slotPanel=0
                    ↑ 卡片多漏出 1px
```

当前之所以能做到「露出比例 19.7%」，**正是靠这层 `overflow:hidden` 硬遮罩**。
一旦放开，露出高度就只依赖卡自身 `height` 约束，任何一次重排都可能让卡身漏出（历史上就漏过 29866 px²）。

→ **只在「阴影需要溢出」的那一层放开，且必须重新加断言**：
- `slot` 的 `overflow` 保持 `hidden`（它是遮罩，不是装饰）；
- 阴影改由 `.cz-astack-crown::after` 画在同层（不外溢到 slot）；
- 断言：`exposedRatio ∈ [18.5%, 21.5%]` **且** `paintedPx - slotHeight <= 0`。

### agy 对两个产品决策的倾向

**决策 A（组合 3 = 4 张 还是 6 张）→ agy 倾向 6 张**
理由：文案承诺六卡；组合 1/2 已承担「一屏无滚动」任务；组合 3 定位是全景工作台，允许 1133 下横向滚动（类比 Logic/Ableton 机架）。

**决策 B（组合 1 = 改文案 4 卡 还是 改实现 2 卡）→ agy 倾向改实现，缩回 2 卡**
理由：给用户最纯粹心智模型；形成 **2 卡 → 4 卡 → 6 卡** 的清晰阶梯：
- 组合 1（2 卡）：极简双联 A + S
- 组合 2（4 卡）：日常重点 A + S + D + Q
- 组合 3（6 卡）：全景工作台 A + B + S + D + R + Q

**Codex 意见：同意 agy 的两个倾向。** 理由：阶梯命名与实现一致后，用户点哪个按钮都不会意外；组合 3 横向滚动是可接受的（机架式交互在 iPad 上有成熟先例）。
