# 徽章卡编号 (No.007) 数据方案

> 触发: dad 2026-09-12 反馈「每个卡片的编号是不是还涉及到 achievements 的后端？这个需要 plan 好」
> 本文件只是方案 (plan)，未动任何代码/DB。拍板后才实施。

## 0. 一句话结论

卡面右上 `No.007` 现在**没有任何后端来源**，是前端硬编码兜底 `"001"`。
推荐 **A 方案**：给 `achievements` 加一列 `card_no`（图鉴编号，一卡一号、永久不变），
一次性回填现有 44 张，新徽章在建卡事务里自动 `MAX+1`，后端两条 API 各加一个可选字段。

## 1. 现状 (实测，非推测)

| 项 | 事实 | 出处 |
|---|---|---|
| 卡面编号 | `no: d.no \|\| "001"` → 真实链路上永远是 `001`；演示页硬编码 `no: "007"` | `static/js/badge-ccg.js:537` / `:14` |
| 领取弹窗数据源 | `/api/badge/unclaimed` 返回 `id, name, type, category, cond_text, description, badge_url, achieved_at`，**无编号字段** | `routes/badge_claim.py:92-136` |
| DB 表 | `achievements` 44 行，主键是 TEXT `id`（`total_60` / `grade_1` …），**无任何编号列** | `sqlite3 .schema achievements` |
| 排序现状 | `sort_order` 36 行为 `0`（老数据）、8 行为 `29~37`（新徽章走 `MAX+1`）；另有 `sort_order_override` 可覆盖 | `badge_db.py:70-76` |
| 规模 | achievements 44 / achievement_stats 25 / achievement_badges 44 | sqlite count |
| 日期 | `achieved_at` 存 `'YYYY-MM-DD'`（如 `2025-10-07`），卡面设计要 `2026年6月16日` | 同上 |
| 星级 | `stars` 同样是前端硬编码（`BADGE.stars`），无后端来源 | `badge-ccg.js:536` |
| 小程序 | `GET /api/achievements`（`minip_api.py:169`）读**同一张表** + `ORDER BY sort_order`；小程序 `badges-hall` 页只显示 name/type/description，不显示编号 | `minip_api.py:183` / `dizical-minip/src/pages/subpkg/extra/badges-hall.vue` |
| 7 日盲盒 | 主题卡不在 `achievements` 表（`THEMES` dict），编号体系与独立徽章无关 | AGENTS.md §Badge 两类 |

**为什么必须排编号而不是直接用 sort_order**：新徽章确实是 `MAX(sort_order)+1`，
但 (1) 老 36 张全是 0，语义已坏；(2) 它同时承担**展示排序**职责，还有 `sort_order_override`；
(3) 编号一旦露在卡面上就是「图鉴编号」，改排序不该改号。

## 2. 方案对比（推荐 A）

| | **A 新增 `card_no` 列** ✅ | B 复用/派生 `sort_order` | C 前端列表序号（现状） |
|---|---|---|---|
| 编号语义 | 图鉴编号，一卡一号永久不变 | 展示位置 | 当次列表下标 |
| 稳定性 | 改排序/改 override 不受影响 | 一改排序就变号 | 每次渲染可能不同 |
| 老数据 | 一次性回填 44 张 | 36 张为 0，仍需回填 | 不涉及 |
| 新徽章 | 建卡事务内 `MAX+1`，与排序解耦 | 继续 `MAX(sort_order)+1` | 不涉及 |
| 小程序 | 新增**可选**字段，老客户端不受影响 | 同 | 不涉及 |
| 成本 | 1 迁移 + 1 回填 + 2 处写入/读取 | 0 迁移，但语义混 | 0 |

结论：B 会污染排序语义、C 撑不住「集卡」概念 → 选 A。

## 3. A 方案落地细节（拍板后按此实施）

### 3.1 DDL（幂等，走 MCP/manageDatabase 留审计）
```sql
ALTER TABLE achievements ADD COLUMN card_no INTEGER;
CREATE UNIQUE INDEX IF NOT EXISTS idx_achievements_card_no
  ON achievements(card_no) WHERE card_no IS NOT NULL;
```
- 幂等写法：先 `PRAGMA table_info(achievements)` 判列是否存在（SQLite 无 `ADD COLUMN IF NOT EXISTS`）。
- 可空：不强制 NOT NULL，避免迁移瞬间炸写入路径（新徽章由写入路径保证有值）。

### 3.2 一次性回填（44 张）
排序规则（推荐）：`category` 分组 → 现有 `sort_order`（0 的老数据按 `created_at`）→ `id`，
从 001 连续编号。dad 可要求手排（给序号表即可，回填脚本读表）。
回填走 MCP 留审计；回填后跑一次校验：`count(*) = 44`、`count(distinct card_no) = 44`。

### 3.3 新徽章写入路径
- `badge_db.py` 加 `fetch_max_card_no()` → `card_no = MAX+1`（与 `fetch_max_sort_order()` 并列）。
- 写 `achievements` 的 INSERT 增加 `card_no` 字段（同一事务，避免并发跳号）。
- **draft JSON 契约**（`data/lib/badge_data/*.json`, `schema_version: 1`）加 **可选** 字段
  `card_no` / `stars`：不填 → `MAX+1` / 默认星级；老 draft 不填照跑（向后兼容，schema_version 不升版）。
  契约文件是 dizical↔skill 的唯一接口，加可选字段不破坏现状。

### 3.4 展示（三处统一）
- 前端 `normalize()`：`no` 取 `d.card_no`，格式化为 `No.%03d`（无值时不显示 `001`，改为显示 `—`，避免假号）。
- `GET /api/badge/unclaimed` 增字段 `card_no`（🟡 部分兼容：新增可选字段）。
- `GET /api/achievements` 增字段 `card_no`（同上，小程序不改也能跑）。
- 顺带修卡面日期：`achieved_at` 的 `YYYY-MM-DD` → `2026年6月16日`（纯前端格式化，不动 DB）。
- 顺带修星级：见 Q3。

### 3.5 编号分册（建议：一册）
银条已显示分类（突破/段位/…），编号再分段会变成两套坐标；建议全库一册 `001–0NN`。
若 dad 想按类别分段（如 `段位-03`），改 3.2 的编排规则即可，不动表结构。

### 3.6 不做（本轮范围外）
- 7 日盲盒主题卡编号（独立体系，另立方案）。
- 卡面视觉改动（dad 已说「其它很不错了不要动了」）。
- `sort_order` 语义清理（与编号解耦即可，不顺手改名/重构）。

### 3.7 跨端登记
后端 API 加字段后 → 更新 `API-CHANGELOG.md`（🟡 部分兼容）+ 评估小程序是否择期显示编号。
