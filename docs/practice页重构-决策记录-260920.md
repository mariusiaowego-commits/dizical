## 2. Q3 的字段调查结果（dad 要求先列出来）

`weekly_assignments.items` 是 JSON 数组，每条是 `{item, item_id, metronome, requirement 或 requirements}`。全量 29 条记录（2025-11-08 ~ 2026-08-01）实测：

| 键 | 出现次数 | 时间跨度 | 与另一键同时出现的次数 |
|---|---|---|---|
| `requirement`（单数） | 49 | 2025-11-15 ~ **2026-05-09** | **0** |
| `requirements`（复数） | 57 | 2025-11-08 ~ 2026-08-01 | **0** |

**结论 1**：两个键**语义相同**（都是"要求正文"），是前后两版录入实现留下的键名差异，**按时间严格分段、从不混用** —— 所以读取端做 `requirement || requirements` 兜底就够，不需要做语义区分。
**结论 2**：分界点在 **2026-05-16**：五月之前写单数、之后写复数（唯一例外是 2025-11-08 那条复数）。

**顺带发现（比键名更要紧）**：早期记录（2025-11 ~ 2026-05）里 `item` 字段不是科目名，而是分类词 —— `要求` / `作业` / `大课` / `Test`，而且大多没有 `item_id`。也就是说这批老数据**无法和科目关联**。设计时要么不显示这批，要么单独放"历史要求"区。**这条要 dad 定**（§6-1）。

**你给的 metronome 结构化方案（我按此建模）**：

| 字段 | 含义 | 取值 / 规则 |
|---|---|---|
| `section` | 切片 / 段落 | 填哪个段落或片段（自由文本） |
| `beat_unit` | 拍值基准 | 选择：♩ / ♪ / ♬ |
| `bpm_min` | 速度下限 | 选填 |
| `bpm_max` | 速度上限 | **必填**（只有一个速度时填这一栏） |
| `notes` | 备注 | 如"前 3 天练 A 速度，后 4 天练 B 速度" |

这解释了为什么"多种节拍要求"不是脏数据：一个科目在一个 stage 里可能同时有 4/4 ♪=80 与 2/4 ♪=69-80、或 tu/ku 两个速度 → 数据结构天然要支持**一个科目多条速度段**。
你另给了两个速度录入交互参考：Pinterest pin `628604060472112191`、`112097478221225231`。
"音符漏写"这条按你的要求变成**提交前校验**（beat_unit 必选）。

## 10. 布局方向升级：两态两套布局（2026-09-20 dad 追加）

1. **老师要求卡与仪表卡同宽**，布局上**关联在仪表卡下方** —— 开始练习后能边计时边看这个科目的本周要求

## 11. 附：`requirement` vs `requirements` 现状结论（2026-09-20 查代码 + 查库）

| 项 | 结论 |
|---|---|
| 语义 | **没有区别**，同一个"要求正文"的两个键名 |
| 单数来源 | 录入端写的：CLI 老师要求解析（`src/cli.py:1269/1273/1283`）与表格导入（`src/practice.py:522-547`）传的是 `requirement` |
| 复数来源 | **落库时被规范化**：`src/database.py:727-733` `save_weekly_assignment()` 明确把 `requirement` 改写成 `requirements`，并保证 `requirements` / `metronome` 键存在 |
| 现在最新在用哪个 | **`requirements`（复数）** |
| 数据侧证据 | 复数最早 2025-11-08、**一直到 2026-08-01（最新一条）**；单数最后出现在 **2026-05-09**；两键从不混用 |
| 读取侧 | 所有读取点都是 `requirements or requirement` 兜底（`app.py:1450/2000/2593/2657/2667`、`config.py:1050/1081`、`practice.py:294`、`cli.py:1098`）→ 现状不会出错 |
| 结论 | 老的单数记录是**规范化逻辑上线之前**写进去的残留；**前端读取照旧兜底即可**。要不要清历史那 49 条（一次性幂等迁移把 `requirement` 改写成 `requirements`，跑完给前后对比 + 审计）—— **待 dad 定** |
