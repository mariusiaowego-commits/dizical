# practice_items 999004 重编号 (2026-08-17)

## 背景

dad 在 config 页新增小科目「双手无名指颤音」后, ID 显示 `999004`, 跟历史 4 位 ID (1001-1346) 不统一。

## 根因

MySQL prod `practice_items` 表 `AUTO_INCREMENT` 当前值被人手动改成 999000+ (推测来自早期 prb 测试脏数据清理脚本或误操作)。后续每次 `add_practice_item` 都会继续分配 999005, 999006... 灾难性 ID 跳号。

| 字段 | 修复前 | 修复后 |
|------|--------|--------|
| 999004 (双手无名指颤音) | item_id = 999004 | item_id = 1347 |
| AUTO_INCREMENT 当前值 | 999004 | 1348 |
| 表行数 | 48 | 48 |
| 历史 ID 范围 | 1001-1346 + 999004 | 1001-1347 (连续) |

## 影响范围 (改前确认)

- `weekly_assignments.items` 引用 999004: **0 行**
- `daily_practices.items` 引用 999004: **0 行**
- `practice_audit_log.input_items` / `result_items` 引用 999004: **0 行**
- 999004 是新建 item, 还没被任何 assignment / practice 引用 → **重编号完全安全**

audit_log 里查到的 999001/999002/999951 等是 sprint-26080803 清理掉的 prb_test 脏数据历史快照, 不需处理。

## SQL 操作 (MCP 审计可查)

```
UPDATE practice_items SET item_id = 1347 WHERE item_id = 999004
ALTER TABLE practice_items AUTO_INCREMENT = 1348
```

## 后续预防

1. **不要再手动改 auto_increment**。如需跳号, 走 `migrate_renumber_item_id.py` (上次重编号在 commit `12b91e3` 2026-05-09)
