## 1 Thing We Learned (1 条关键工程沉淀)

- **「Demo 已实现」≠「生产已交付」——行为性需求必须在 PR 描述逐条对账，仅靠截图验收会系统性漏掉**：
  上一 sprint（26091601）的验收里，「列表态彻底静态化（零监听器 / 无 hover tilt / 无 idle drift）」在本地 Demo 中已完整实现并被目视认可，但生产合流沿用了既有实现路径，卡墙**仍然 hover tilt** 且每卡仍绑 6 个 pointer 监听器。两者截图看起来都对——差别只在**性能行为**上，而性能行为在截图里不可见。
  本轮同样的模式再次出现：dad 验收后提出的「加载慢」问题，本质上也是**截图无法暴露的性能维度**，最终被明确切出为独立专项 sprint。
  **规则**：Demo 阶段任何被 dad 口头认可的**行为性**需求（性能 / 监听器数量 / 动画循环 / 降级路径 / 资源体积），必须在 PR 描述里单列一节「Demo 已实现 → 生产是否同样实现」，逐条标注 `已实现` / `未纳入` / `沿用既有实现`。凡是「看得见的设计 + 看不见的行为」组合，视觉验收必须搭配一条量化指标（帧率 / 监听器数 / 资源体积 / 请求数）才算闭环。
