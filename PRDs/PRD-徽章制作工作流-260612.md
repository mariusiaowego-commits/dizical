### 0.1b V2.1 架构 (2026-06-14)

V1 的 4 步表单 + 6 步流水线 (dizical 内调 hermes subprocess) 已废弃. V2.1 改为 **3 步解耦流程**, dizical 和 hermes 各自独立:

| 步骤 | 执行者 | 动作 | 产物 |
|------|--------|------|------|
| **STEP 1** | dizical (浏览器) | 填元数据 → `POST /api/badge/draft` | `data/lib/badge_data/{draft_id}.json` |
| **STEP 2** | hermes agent | `/badge-image` skill → image_gen + 去背 + 落盘 | `.tmp/{draft_id}_v{n}.png` + draft.json image 字段回写 |
| **STEP 3** | dizical (浏览器) | `POST /api/badge/commit-from-draft` | 三表写入 (achievements + achievement_stats + achievement_badges) |

**核心设计原则**:
- **文件契约是唯一接口**: `lib/badge_data/{draft_id}.json` 是 dizical 和 hermes 的唯一通信方式
- **进程隔离**: dizical 不调 hermes, hermes 不调 dizical 的 DB
- **schema_version 锁定**: draft JSON 的 schema_version 字段锁定 v1, 变更需版本升级
- **calc 跟生图完全解耦**: hermes skill 不管 calc 逻辑. 新 badge 的 calc 走 `/calc-apply` skill (git apply patch → PR → dad merge)

**hermes skill 装 3 profile**:
- `~/.hermes/profiles/dizical/skills/badge-image/SKILL.md` (主)
- `~/.hermes/profiles/coder/skills/badge-image` (symlink → 主)
- `~/.hermes/skills/badge-image` (symlink → 主)
- calc-apply 同理

**Portal 降级**: Nous Portal 不可用时, skill 写 1x1 placeholder PNG 到 `.tmp/`, image.path 字段指 `.tmp/` 路径, commit 仍能跑 (图片占位, 后续补生图).

### 0.2 范围限定（关键！）

**dizical badge 有两类**：
1. **独立 badge** — `seasonal` / `milestone` 单一成就，存 `achievements` 表
2. **7日打卡盲盒** — `ok_sea` / `rapunzel` 主题，存 `THEMES` dict，7 张同主题图联动

> **本 PRD 范围 = 仅 ① 独立 badge**。盲盒主题（②）不在本次需求内，相关代码（`THEMES` 注册中心、rapunzel enamel pin 策划）完全不动。

**locked 态实现**（用户已确认）：
- 运行时**完全靠前端 CSS 灰度遮罩**，不依赖 locked PNG
- 代码位置：`app.py:517`（注释明确写 "灰化由 CSS .b-card.locked .b-img { grayscale(1) } 处理"）
- CSS：`achievements.html:178/325` + `badges.html:89` 三处 `grayscale + brightness/saturate`
- 历史 `static/badges/grade_*-l.png`（生铁轮廓）已不在 UI 使用，本流程**不生成** locked 图

### 0.3 目标
**一个浏览器页面 + 一条流水线**，让用户：
1. 选 / 填 badge 元数据（id、名称、典故、type 标签、category、seasonal/milestone 决策依据）
2. 写 placeholder 描述 — **支持 AI 草拟或手工填**（用户用 alma 等 agent 出 placeholder 时可粘贴）
3. 点"生成" → 后端自动跑 6 步流水线
4. 在前端看到预览 + 红底透明验证图
5. 点"上线" → 写入 `achievement_badges` / `achievement_stats` / `achievements` 三表 + 同步 BADGE_URLS
6. **批量模式**：基于已认可的 badge，生成同风格 N 个新 badge

**核心承诺**：前端产出 badge 必须跟 `static/badges/` 下 68 个现有图视觉一致（enamel pin · chibi Q版 · 珊瑚红 + 6 色 · 厚金边）。

## 2. 用户故事 (User Stories)

> **角色**: 爸爸（开发者兼产品经理，唯一操作人）
> **前置条件**: 已登录 kid-app，进入 `/config/badge`

**US-1 元数据填写**
> 爸爸在新 badge 页面填写：英文 id（`lucky_61_2026`）、中文名（幸运六一节）、分类标签（突破/段位/...）、category（milestone/seasonal）。
>
> 验收：id 在数据库里**没有重复**（实时查 `achievements` 表）；category=seasonal 时要求选 seasonal_type（daily/weekly/monthly/stage）。

**US-2 placeholder 来源二选一**
> Step 2 顶部 radio：
> - (A) **我已经有 placeholder**：textarea 让用户粘贴英文 placeholder（典型来自 alma 等 agent 输出）
> - (B) **AI 草拟**：用户填"典故来源/参考"（中文），后端调 Gemini 2.5 Flash 一次，输出英文 placeholder 草稿（30-60 秒），用户在 textarea 里**继续编辑**直到满意
>
> 验收：无论选哪个，最终都进 enamel pin 模板的 `[PLACEHOLDER]` 槽位，下方实时显示组装好的完整 prompt。

**US-3 典故与计算模板**
> - 典故 / 描述（多行，可 200+ 字符，>200 字符前端警告"记得 `\n\n` 分段"——来自 `docs/badge-workflow.md` line 124 经验）
> - display_format（解锁条件模板）
> - 计算逻辑模板选已有 streak_N / total_N / top1/2/3 / first_log / all_items / double / grade_N / daily_checkin_N / early_riser 三种 / lucky_61_YYYY / "暂不绑定"

**US-4 触发生成 + 实时进度（SSE）**
> 点"开始生成" → SSE 推送：① 校验 ② 写 prompt ③ 调 image_generate ④ 拿图片 ⑤ 去背 ⑥ 写临时预览路径
>
> 验收：每步带 status 文案；失败带 stage 标识（"步骤 ③ FAL 调用超时"）。

**US-5 红底透明验证 + 用户决策（不自动重做）**
> 渲染区显示：① enamel pin 原图（白底）② 红底透明验证图（来自 `dedupe_bg` 经验）。爸爸确认 alpha 正常。
>
> 验收：若自动去背后 `Image.open(p).mode != 'RGBA'` 或红底预览出现白方框 → 前端**展示 3 个用户决策按钮**（用户 2026-06-12 拍板，不自动重做）:
> - **重新生图**：返回 Step 4 重跑 FAL 调用（产生新版本 v+1，旧版本保留）
> - **接受当前结果（带白底）**：直接进 Step ⑤ 上线，**警示文字**告诉用户"上线后 kid-app 会显示白方框，需要等有空再人工去背"
> - **取消**：放弃这个 placeholder，**不写入 DB**
>
> 跟历史 wiki 经验 `docs/badge-workflow.md` line 87 ("lucky_61_YYYY 5 张图忘了去背"导致显示白方框) 对齐 —— 失败兜底**必须留给人判断**，不强行重做。

**US-6 批量模式（仅 milestone/seasonal 同 category 内）**
> 单 badge 上线成功后，前端弹"基于此 badge 批量生成 N 个同风格 badge"按钮 → Step 2 起走**简化的"只填 placeholder N 次"流程**，跳过典故/计算逻辑/元数据（继承已上线 badge 的所有元数据，只换 placeholder），直接进 Step 4 生成循环。
>
> 验收：
> - N 个 placeholder 一次性粘贴（每行一个），逐个生图，逐个红底确认，逐个"通过/重试/跳过"
> - 任何一次失败只影响该次，其他正常入库
> - 最终一次性写 N 行 `achievements` + N 行 `achievement_badges`（milestone 还要 N 行 `achievement_stats`），统一 sort_order
> - 失败的可后补，前端不阻塞其他通过项

**US-7 上线**
> 点"上线" → 二次确认 + PIN → 写三表 + 同步 `BADGE_URLS` + 写 image-gen.md 记录
>
> 验收：返回 200 + 新 badge id 出现在 `/badges` 页面（server 不需要重启，下次 `/badges` 渲染就拿到新图，因为数据是 DB 驱动的 — 配合 §4.2 BADGE_URLS 改 DB-driven）。

**US-8 计算逻辑代码片段输出**
> 上线成功后，前端弹"待贴代码" modal，展示一段 Python 模板（用户选中的 calc 模板对应代码）:
> ```python
> # 请复制到 src/achievement_definitions.py 的 _calc_milestone() 里:
> if aid == "your_id":
>     return CalcResult(
>         achieved=..., 
>         computed_value=...,
>         extra=None,
>         achieved_at=None,
>         "显示条件文案"
>     )
> ```
> 验收：modal 可一键复制代码，不强制阻挡（允许跳过）。进度条依赖此代码，没贴之前新 badge 进度显示 0。

**US-9 失败回滚**
> 任何一步失败 → 后端清理：① 删除临时文件 ② 撤销已写入的 DB 行 ③ 前端展示错误信息 + 重试按钮
>
> 验收：刷新页面没有"半完成"的孤儿数据。批量模式下只回滚当次，不影响已通过项。

## 5. 风险与开放问题

### 5.1 已知风险
1. **FAL 调用时长** 30-60s，用户可能等不及 → SSE 实时推状态条缓解
2. **BADGE_URLS / BADGE_FILES 改 DB-driven** → 用读 DB + 内存 cache 60s（避免每请求查库）
3. **PIL 去背** 不是 100% 干净（红底/渐变可能误判）→ 前端红底预览 + **3 个用户决策按钮**（重新生图 / 接受带白底 / 取消），不自动重做（用户 2026-06-12 拍板，参考 `docs/badge-workflow.md` line 87 历史教训）
4. **calc logic 不自动注入** → 上线后新 badge 进度会显示 0 直到人贴代码（V1 trade-off，可接受）
5. **PIN 验证** → 沿用 `config-blindbox` 模式（localStorage + 入口检查），不发明新东西
6. **批量模式 placeholder 数量** → 限制 N ≤ 20（防止长 prompt 撑爆 hermes chat 命令行）
7. **批量模式失败累计** → 任何一次失败提供"重试/跳过"二选一，跳过的不入库但其他继续
8. **盲盒 = 7日打卡盲盒 = 跟本 PRD 完全无关** → 验证新代码时**不**碰 THEMES dict / 7 张同主题图 / `config-blindbox.html`（用户 2026-06-12 拍板）
9. **Nous Portal 状态监控** (用户 2026-06-12 拍板):
   - dizical profile portal auth 失效 → 启动 fail-fast + 前端状态红 + Step 4 按钮禁用
   - Tool Gateway 路由变更（用户改 hermes model 后 image generation 不再走 portal）→ 生图质量降级，需用户切回
   - portal 调用本身的 latency (~2s) 加在所有 Step 4 SSE 开头，影响体验 → 已接受（30-60s FAL 调用是更大瓶颈）
10. **hermes subprocess 子进程** (dizical 服务里 spawn `hermes chat`) → 不能用 shell=True (moni `default_worker.sh` 用 list argv 安全) + 必须设 timeout + 必须吃异常不挂 uvicorn

### 5.2 开放问题（用户已部分回答）

**Q1. locked 版生成 — ✅ 已定：** 不生成，locked 态用前端 CSS 灰度遮罩（`achievements.html:178/325` + `badges.html:89` 已有现成实现）

**Q2. AI 草拟 placeholder — ✅ 已定：** V1 包含，作为 placeholder 来源二选一之一（"我自己写" vs "AI 草拟"）。AI 用 Gemini 2.5 Flash（参考 `subject_info.py` 的实现，line 88-95 fallback 模式）。`GOOGLE_API_KEY` 已配置。

**Q3. 批量生成 — ✅ 已定：** V1 包含，但**仅"基于已认可 badge 衍生 N 个"**（不是空表批量填表）。每个新 badge 继承已认可 badge 的所有元数据（id/名称/category/display_format/sort_order 区间），只换 placeholder。N ≤ 20。

**Q4. calc logic 注入 — ✅ 已定：** V1 **不做**自动注入。改用"前端弹代码片段让人工 review"模式 —— 提交后输出 Python 代码模板，让用户复制到 `src/achievement_definitions.py`。原因：① agent 写生产 Python hot path 风险高 ② badge 不重启服务就上线的核心承诺是图+数据，不依赖 calc。V1.1 再做自动注入 + git diff preview + dry-run。

**Q5. 估算工作量 + 拆 PR：**
